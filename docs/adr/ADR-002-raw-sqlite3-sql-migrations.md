# ADR-002: Use raw sqlite3 with numbered SQL migrations

**Status:** Accepted
**Date:** 2026-11-08
**Deciders:** Srimugunthan

---

## Context

The PRD (§13) specifies FastAPI with SQLite and a migration tool "for example Alembic". The riskiest behavior is transactional SQL: import upserts that must never lose groups or history (FR-6, FR-9), stage moves with history (FR-43), and bulk stage apply with undo (FR-58, FR-60). Data is a single local user's contacts, up to about 10,000 rows. In the design interview (Q3), SQLAlchemy 2.0 with Alembic was the recommended option, but the owner chose raw `sqlite3`.

---

## Decision

We will use the standard-library `sqlite3` module with hand-written parameterized SQL in a repository layer, with one short-lived connection per request, foreign keys on, WAL mode and a single uvicorn worker. Schema changes are numbered `.sql` files in `migrations/`, applied at startup in order inside a transaction, with the version tracked in `PRAGMA user_version`. Before applying any pending migration, the app backs up the database with SQLite's backup API and keeps the last 5 backups.

---

## Alternatives Considered

| Option | Pros | Cons |
|--------|------|------|
| SQLAlchemy 2.0 + Alembic | Mature; autogenerated migrations; named in the PRD | Extra dependency and abstraction over SQL that is already simple |
| SQLModel | Less boilerplate | Younger project; same abstraction cost |
| **Raw sqlite3 + SQL migrations (chosen)** | No ORM dependency; full control of transactions, upserts and `ON CONFLICT`; matches the single-file DB | Hand-written SQL and row mapping; no autogenerated migrations |
| yoyo-migrations / hand-rolled version table (migration options) | Existing tooling | Another dependency, or more custom code than `PRAGMA user_version` |

---

## Consequences

**Positive:**
- Few dependencies; the whole data layer is readable SQL.
- Direct control of the transactional import and bulk-apply logic.
- The pre-migration backup protects against the main way of losing data.

**Negative / Accepted Tradeoffs:**
- All SQL, row mapping and migrations are written and tested by hand.
- No autogenerated migrations; schema changes need care.
- Moving to another database later would mean rewriting the repository layer.
- Tests run against a real temporary SQLite file, since mocks can't check the SQL.

---

## Implementation notes (2026-11-08)

Built as decided. Seven numbered migrations exist (`001_baseline` to `007_bulk`); each feature adds only its own tables, and later columns on existing tables are added with `ALTER TABLE ... ADD COLUMN` (for example the stage columns on `group_members`). The runner splits a file into statements with `sqlite3.complete_statement`, runs each migration in its own transaction, and sets `PRAGMA user_version` inside it, so a failing migration rolls back and the app refuses to start. The pre-migration backup is taken only when the database already has data (version above 0), and the last 5 are kept. All of this is covered by pytest. Python is 3.13 via `uv` (decision 70). Data-model additions made during the build are in decision 61.
